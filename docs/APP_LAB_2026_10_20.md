# App Lab — first release, 20 October 2026

Historical first-release record. The owner's subsequent interface and editable-code request supersedes the Blockly-only editor and text-coding exclusion below; see [the interface/code follow-up](APP_LAB_INTERFACE_CODE_2026_10_20.md). Privacy, gallery, curriculum and execution boundaries remain in force.

Owner-approved scope: drag-and-drop multi-screen design, editable event blocks, live preview, project save/export and project-local data tables. Keep KodeArcade's identity and leave curriculum implementation unchanged. The supplied Code.org screenshots inform workflow, not a compatibility or feature-parity claim.

## Entry points and saving

- Public preview: `/#/app-lab`, also linked from the course chooser. Saves only under `kodearcade-app-lab-v1:preview` in this browser. People sharing the browser can see these apps; no private-account claim is made for public preview.
- Student dashboard: App Lab links for assigned Grades 3–6, opening `/#/student-play/grade-N/apps`. Enrollment and assignment checks remain in force. Grades 1–2 do not acquire an App Lab assignment or access through a guessed path.
- Student work uses the existing memory-only activity storage, revisioned account progress, conflict handling and encrypted device recovery. It never imports public localStorage. Existing session expiry/sign-out protections apply.
- Each course has its own gallery of up to eight apps. A new app retains earlier ones. App deletion is explicitly confirmed; it is permanent in this first release, so download a backup first. The only remaining app cannot be deleted.
- Download exports the whole gallery. Import validates it and adds copies with new project UUIDs; it does not overwrite existing apps. Invalid/oversized imports leave existing work unchanged. A corrupt saved copy is not silently overwritten: recovery download and an explicit valid recovery import are available.
- Storage failure leaves edits in memory, reports failure and offers backup/retry. “Saved on this device” is not displayed for a failed write. Account save/conflict states use the existing SaveFeedback controls.

## Working features

### Design

Up to six screens per app with a selected starting screen and individual background colors. Add, rename and delete screens. Add buttons, labels, text inputs, text areas, dropdowns, checkboxes and sliders; drag from the toolbox or click to add, then drag to move. Arrow keys move a selected control by one design pixel; Shift uses ten. Property fields offer an equivalent way to place/size it.

Controls have globally unique IDs, text, width/height, X/Y, text/background colors, font size and hidden-at-start state. Dropdown options, checkbox starting state and slider starting value are editable. Duplicate creates a new control ID, not a second script. Renaming a screen/control updates matching code references; deletion deliberately keeps code for children to repair rather than silently deleting their scripts.

The app stage uses 320 × 480 design coordinates, origin at the top left, positive y downward. It is separate from Byte Lab's centered, upward-positive coordinate system. The preview scales to available width without changing authored geometry. Existing lesson mobile layouts are unchanged.

### Code

Real Blockly blocks, not preprogrammed mock controls:

- Run and control click/change events.
- Open a screen, show/hide a control, read text/number/checked state and set displayed text.
- Literal text/numbers, join, arithmetic, comparisons and Boolean combinations.
- Named app-level variables, Print output, if/else and counted repeats.
- Project table row count, cell read and runtime cell update by table, zero-based row and named column.
- Undo/redo, fit code, category palette, live code serialization and reload. Narrow screens use a horizontal native flyout to preserve canvas width.

“Add event blocks” in Design creates an ordinary inspectable event with a Print action. The keyboard helper inserts unconnected blocks; it is not complete nonvisual connection/field editing. This first release does not claim full keyboard/screen-reader access to Blockly programming.

### Run and debug

Run constructs a fresh runtime from the saved design. Inputs, event responses, variables and table updates exist in that runtime, not in the authored project. Stop restores the design preview. The next Run restores the starting screen, controls and data, and initializes variables only through authored Run blocks. Runtime state is not saved automatically.

The collapsible console displays up to 30 Print messages, current variables and actionable errors. Missing references, unset variables, wrong value types, division by zero, invalid table cells and execution limits produce errors. There is no step debugger or general JavaScript console.

### Data

Create/delete project-local tables, add/delete rows, add/rename columns and edit cells. Values recognize numbers and `true`/`false`; other values are text. These tables travel inside the project backup/account save. They are **not** shared databases, public datasets or live API connections. Use fictional items, scores and story data, not personal student information.

Runtime table updates reset on the next Run. Persistent runtime records, key/value services, CSV imports, external datasets and collaborative data are outside this release.

### Starters

- Hello, app!: input → text join → greeting on a second screen → back button.
- Tap counter: Run initializes a variable; clicks increase and display it.
- Animal explorer: read a fact from the bundled project-local example table.
- Blank app: one screen and a Run block.

All behavior is editable in ordinary blocks. Starter names are examples, not separate runtime branches.

## Safety and compatibility

`shared/appLab.ts` owns the allowlisted, versioned project contract. Unknown input is size/depth checked before recursive validation. No eval, Function constructor, arbitrary JavaScript, remote fetch, injected HTML, external images, camera, microphone or public publishing exists in child programs. React renders user text as text.

Limits: eight apps per gallery, six screens, 40 controls, 120 serialized blocks with bounded connection depth, six tables with 50 rows/eight columns each, 20 runtime variables, 300 characters per text/cell, 1,000 operations per event/start group, 10,000 per run and 500 events per run. Numeric results are finite and within ±1,000,000. Gallery JSON is bounded to 220,000 characters with a separate structural-node bound. Imports are bounded to 700,000 file bytes. The existing total course-payload limit still applies: saving a large combination of Byte Lab art, drawings and apps can require reducing or backing up work.

Account progress gains an optional validated `appLab` field; no database migration, new course key, curriculum version change or new external service is required. An older client omitting this field cannot erase it. Existing protected achievements, Byte Lab galleries, drawings and quiz records retain their contracts. App Lab runtime scores and app completion do not award course stars or enter teacher reports. Private app content is excluded from report summaries.

Frontend and backend must deploy together for account saves to accept the new field. This implementation pass does not push, merge, deploy or migrate production. The proposed V3 curriculum map remains on hold; App Lab is not yet integrated into its lessons or assessments.

## Verification record

The user story is: public course chooser or assigned student dashboard → App Lab designer/code/data → Run → private save/backup → reopen. Account saves flow through activityStorage → collectCloud → existing progress API → validated private JSON document → hydrateCloud → restored app. Browser tests use synthetic API fixtures; backend integration tests use a local ephemeral PGlite database. Neither is a production-session test.

- Final full unit regression: 44 files, 1,825 tests passed, including the two dropdown regression cases. The focused App Lab suite passed all 41 tests.
- Focused server progress/recovery/deployment integration: three files, 29 tests passed, including a new App Lab privacy/round-trip/legacy-omission case.
- Final browser regression: all 21 tests passed across desktop, phone and tablet (12 App Lab checks and nine incumbent creative-dashboard checks). All nine Design/Code/Data captures were refreshed and reviewed. Initial phone checks identified missing accessible names on Import/Download and a selected-tab hover contrast defect, both corrected. Tests use Blockly's actual desktop field and mobile dialog controls.
- Independent finish review identified two material fixes: reject nonexistent dropdown options before changing runtime state, and make the skip link focus the workspace without replacing the hash route. Both have implementation changes and dedicated regression assertions. The final verdict is **ship**, with both findings resolved; this scores those fixes, not production certification. See `.impeccable/review/app-lab-finish.md`.
- Final production build and server typecheck both passed (exit 0). Existing large-chunk and dependency annotation warnings remain; this is not a claim of zero warnings. Production was not deployed or tested during this implementation pass.

Not included: editable text coding, general-purpose functions, while loops, image/audio assets, turtle/canvas commands, charts, recordings, network APIs, live shared data, publishing/remix links or Code.org project import. These need separately specified follow-up work, not inactive buttons pretending to implement them.
